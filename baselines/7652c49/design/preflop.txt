* **pot_odds computed wrong preflop** (common when blinds/ante/raise-to are interpreted incorrectly),
* **strength proxy scaled/biased too low for 3-card + discard**, or

## PRD: Preflop Strategy Overhaul + Self-Play Harness Integration

### 1) Background & Problem

Toss/Hold’em variant:

* 3 hole cards preflop.
* After a 2-card flop, player discards one of the 3 hole cards.
* Showdown uses 6-card board (per your rules).

Observed issue:

* In self-play, bots are folding ~100% preflop in multiple seat-swapped suites → trivial outcomes, zero learning/signal.

### 2) Goals (Must-Haves)

1. **Nontrivial preflop play**: avoid pure fold equilibrium in self-play.
2. **Speed**: no preflop simulation/Monte Carlo.
3. **Deterministic**: identical inputs → identical outputs (given the same seed).
4. **Compatibility**: Python 3.7 + pkrbot backend + offline constraints.

### 3) Non-Goals (Explicit)

* No opponent modeling preflop in v1.
* No GTO solving, no preflop abstraction training.
* No changes to postflop logic in this milestone (except logging hooks if needed).

---

## 4) Product Requirements

### 4.1 Decision Policy Overview

Implement a dedicated preflop decision function:

**`_preflop_open_decision(state) -> Action | None`**

* Computes:

  * `strength = preflop_strength(hole3, position, maybe stacks?)` (existing)
  * `pot_odds = cost_to_call / (pot + cost_to_call)` (ensure definition is consistent)
  * `pos_adj = -0.03 for SB/button/in-position, +0.03 for BB/OOP`
* Applies:

  1. **Hard thresholds** derived from `pot_odds` and your margins.
  2. **Bucketed mixed actions** to avoid deterministic fold.
  3. **Safety bounds**: min-raise, cap, legality checks.

If `_preflop_open_decision` returns `None`, fall through to existing “standard pot-odds logic” (backward compatibility).

### 4.2 Pot-Odds Thresholds (Baseline)

Use these as first-pass gates:

* **Call threshold**:
  `strength >= pot_odds + call_slack + pos_adj`
  where `call_slack = +0.03` (as you propose).

* **Raise threshold**:
  `strength >= max(pot_odds + 0.20 + pos_adj, 0.50)`
  (the absolute floor prevents “raise never happens” when pot_odds is tiny).

**Important**: These thresholds must be interpreted in the same scale as `preflop_strength()`. If `preflop_strength()` is not calibrated to something like “equity proxy” in [0,1], the thresholds must be rescaled.

### 4.3 Mixed Action Buckets (Anti-Triviality)

We need a **deterministic mixed policy** driven by a seeded RNG (details below).

#### SB / In-Position (looser)

Let `s = strength`.

* If `s >= 0.58`: Raise with 65% else Call (or check if free).
* Else if `s >= 0.40`: Call with 60% else Fold.
* Else if `0.30 <= s < 0.40`: Call with 30% else Fold.
* Else: Fold (unless check is available; then Check).

#### BB / Out-of-Position (tighter)

* If `s >= 0.62`: Raise with 40% else Call.
* Else if `s >= 0.35`: Call with 60% else Fold.
* Else if `0.30 <= s < 0.35`: Call with 25% else Fold.
* Else: Fold (or Check if free).

**Rule precedence**:

1. If facing a bet/raise, “Check” is not available; resolve among Fold/Call/Raise.
2. If Call is free (cost_to_call == 0), treat “Call” as “Check” to avoid inflating pot needlessly (unless you explicitly want probing bets preflop).

### 4.4 Safety & Legality Requirements

* Never raise if raising is illegal or `min_raise` not defined.
* Never raise below `min_raise`, never above cap (use existing raise_size logic).
* If raise is selected but illegal:

  * degrade to Call if legal, else to Check if free, else Fold.

### 4.5 Deterministic Randomness (Hard Requirement)

Mixed action must be reproducible.

* Use a deterministic PRNG seeded per-hand and per-decision, e.g.:

  * `seed = hash(hand_id, player_id, street="preflop", action_index)`
* Use `random.Random(seed).random()` (Python 3.7 compatible).
* Do **not** use global RNG state.

You already added engine logging—extend it so it’s actionable:

## 6) Acceptance Criteria (Testable)

### Suite-level (your stated criteria, tightened)

Run: **10×1k seat-swapped** self-play suite.

Pass if all are true:

1. **Preflop fold rate < 90%** overall AND for each seat (SB and BB).
2. **Nonzero call and raise counts** in the parsed logs (both seats).
3. **EV/hand != 0** in at least one matchup *and* nontrivial pots occur (e.g., average pot size > blinds-only baseline).
4. **No timeouts / no measurable perf regressions**:

   * preflop decision time stays within current budget (define budget in ms if you have one; otherwise compare before/after median).

### Debugging “must-detect” conditions (fail fast)

If any of the following occur, the harness flags RED:

* `pot_odds` outside [0,1] for any hand.
* `to_call > 0` but legal_actions has no Call and no Fold (rules bug).
* `raise selected` >5% but `illegal_raise_degrades` >50% of raises (min-raise/cap mismatch).

## 8) Risks & Mitigations

### Risk: Too loose → exploitable / high variance

Mitigate with:

* Slightly higher BB thresholds (already).
* Cap max raise frequency by bucket.
* Enforce “raise floor” only when pot_odds indicates enough value (keep the `max(pot_odds+0.20, 0.50)` but consider raising the 0.50 if still spewy).

### Risk: Still too tight → trivial fold remains

Mitigate with:

* Increase mid-bucket call probabilities (esp. SB 0.30–0.40).
* Add “check when free” to avoid fold leakage when to_call==0.

### Risk: Determinism broken by RNG usage

Mitigate with:

* local `random.Random(seed)` per decision; never global RNG.

## 9) Open Questions (I’m not blocking v1 on these; we’ll ship with defaults)

These are the only uncertainties that matter, and we can answer them via self-play metrics:

1. **Strength scale validation**: Is `preflop_strength()` empirically centered such that 0.30–0.60 is meaningful?

   * If it’s compressed (e.g., most values <0.25), your thresholds will never trigger.
2. **Pot odds definition**: Are you computing pot odds as `to_call / (pot + to_call)` or something else?

   * A wrong denominator can push thresholds too high.
3. **Position mapping**: What exactly is “SB/in-position” in your engine? Dealer button? Heads-up SB acts first preflop but is IP postflop; your note says “SB/in-position” so I’m assuming your variant’s action order or discard order makes SB informationally advantaged. If that’s wrong, swap the adjustments.
